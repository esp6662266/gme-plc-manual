# GME 설비 매뉴얼 확장 작업표준

표준 버전 **GME-STD-1.0.0** · 2026-10-11

기준 프로그램 **v1.3.0 / 0253c7a5694e6f406c2414813fa2f19ed80ec32f** · 기준 설비 **BC01(P01)**

실행 모델 **GPT-6.1 Sol / Ultra** · 현재 상태와 다음 작업은 [EXPANSION-WORK.md](../../EXPANSION-WORK.md).

## 1. 목적과 작업 범위

BC01의 자료 추적 깊이, 화면 흐름, 수리·관찰·기록 보존 수준을 다른 설비에 적용한다. BC01의 태그·알람·회로·항목 수를 복제하지 않는다. 새 원본 근거로 해당 설비의 내용을 작성한다. 이미 있는 FN04·AB01 등의 완료 분석은 보존하고 부족한 연결·표시·검증만 보강한다.

사용자는 2026-10-11에 **실제 대장 기준 중복 정리·기존 제외 유지**를 선택했다. 기존 문서의 “BC01 단독, 전체 확대 보류”는 v1.3.0 구현 당시 기록이다. 이 표준은 후속 확장 계획이며 실제 작성 여부는 최신 사용자 요청과 EXPANSION-WORK.md로 판단한다. 시뮬레이터 중지와 실제 PLC/현장/보호값 변경 금지는 계속 적용한다.

현재 요청에서 만드는 것은 표준·스킬·작업대장·인계 문서다. 설비 작성은 이 표준을 전달받은 후속 작업에서 시작한다.

## 3. 진행 순서

### 준비 단계 PREP-01 — 공통 구조를 확장 가능한 상태로 만들기

1. Git 상태·현재 main·원본/중지 자산·BC01 기준을 보존한다. 사용자 수정이 있으면 별도 백업 또는 작업 분리 후 진행한다.
2. 현재 BC01 전용 프로파일, 화면, 검색/URL 상태, 기록 도구, 검증 기대치를 조사한다. 변경 전후 출력 파일 목록을 정한다.
3. BC01 기능을 유지하면서 설비별 프로파일·적용 기능·근거 묶음·안정된 기록 키를 받는 공통 계층을 설계하고 필요한 부분만 구현한다. 현재의 P01 전용 복원을 다른 설비에서 이미 쓸 수 있다고 표시하지 않는다.
4. 생성기 호출 관계를 확인한다. build-control-spec.py는 build-program-model.py를 자동 호출한다. **금지 경로를 분리하고 중지 정책을 확인하기 전 실행 금지.** 시뮬레이터를 수정·생성·실행하여 분리 여부를 시험하지 않는다. 정적 호출 확인으로 분리하고 정적 문서 작업만 허용한다.
5. build-all-in-one.py는 networks/network-*.html의 앵커·스타일도 수정한다. 영향 목록과 보존 해시를 확인한 후 필요한 생성기만 실행한다.
6. BC01 회귀 검사를 유지하고 설비별 검증을 추가한다. 기존 단언을 제거하거나 수량만 바꿔 통과시키지 않는다.
7. 준비 완료 근거를 기록한 뒤 FN04(P02)를 첫 시범 대상으로 진행한다. 시범 완료 전 다수 설비에 템플릿을 일괄 주입하지 않는다.

### 2차 — 133개 후보

INVENTORY.json의 phase2만 대상으로 삼는다. 부모 문서와 직접 연결 근거를 먼저 확인한 후 자식 항목을 진행한다. 독립된 동순위 항목은 대장의 depth → group → catalog_id 순서를 기본으로 하되 제어 의존성 때문에 바꾸면 이유를 기록한다. motor/gate/motorvalve → 계측·조절/공통 기능 → 본체·하위 부품 순서도 근거 의존성에 따라 조정할 수 있다.

첫 유형은 한 설비로 검증하고, 같은 유형의 후속 작업도 설비 한 개씩 작성·검토·저장한다. 처음부터 수백 개를 “완료”로 일괄 생성하지 않는다. 제외90과 부모 범위 보류7은 자동 재개하지 않는다.

### 유형별 필수 예외

- **모터·팬:** 본체/모터/냉각팬/브레이크/공동 인버터를 구분한다. FN04 두 모터·설정0·제한 쓰기, FN03 두35초 SD, FN06 별칭 알람은 해당 원문으로 다시 대조한다.
- **PV 게이트:** 명령→EV→실제 위치→MEM_OPEN/CLOSE를 분리한다. 기억 비트는 실물 센서가 아니다. PV01/PV02 타이머를 공통 값으로 만들지 않는다.
- **MV 댐퍼:** 방향 출력·반대 출력·리미트·엔코더·교정·PID를 구분한다. 공유 네트워크의 다른 설비 조건을 가져오지 않는다. MV03의 S5T#150S와 별도150ms 선언을 같게 만들지 않는다.
- **BR01/외부 제어기:** GME 요청·허가·응답·리셋만 직접 근거로 판단한다. 외부 연소제어기의 화염·점화·퍼지·안전 내부 순서를 추정하지 않는다.
- **계측/아날로그:** 센서→변환기→채널→원시값→환산/단위→범위 오류→제한/PID→출력→관찰값을 추적한다. 호출 조건·복수 쓰기·채널 미확정을 남긴다.
- **본체/수동 설비/기계 부품:** PLC 전용 신호가 없으면 없는 상태를 설명한다. 주변 센서·공통 알람을 본체 소유로 바꾸지 않는다. 체인·스프로킷·베어링에 신규 PLC 알람을 만들지 않는다.
- **client/software/공통 기능:** 물리 설비로 취급하지 않고 기능 소유자·호출자·자료 흐름을 작성한다. 적용할 물리 회로가 없으면 이유와 비해당 상태를 남긴다.

## 5. 근거 작성 표준

핵심 주장마다 “원본 파일 + 페이지/행/네트워크 + 대상 선언/핀 + 해석 + 미확정 경계”를 붙인다. 원본에서 확인한 사실, 사용자 진술, 파생 자료, 가설, 현장 관찰을 구분한다.

1. 실제 설비/도면 대응 → PLC 백업과 XML 선언 → HMI 주소/이벤트 → 전기·단자·케이블 → 계측 환산 → 알람/정지/복구 → 관찰 기록의 연결을 만든다.
2. program-model.json·검색 색인·제어 명세는 탐색용 파생 자료다. 핵심 조건은 decoded-original XML의 Global/Local, Part/Wire/ORef/CRef, UID/RID/NID와 선언·상수로 대조한다.
3. AND/OR/NOT, 네트워크 순서·호출, Set/Reset, 타이머 종류/원문 단위, 다른 쓰기를 보존한다. 해석되지 않은 ENO/out은 미해석으로 남긴다. 연결만으로 실행 의미·최종값을 확정하지 않는다.
4. 도면의 FG와 PDF 페이지를 구분하고 제목·개정·단자 양 끝점·케이블 번호/종류·중복 행을 보존한다. 필요한 도면은 원본 렌더로 시각 확인한다. 승인 시공도와 참고 견적/설계 자료를 구분한다.
5. BC01의 Tag_51(%T39)은 FAULT/INV에서 공유하는 PLC 타이머이며 HMI 태그로 분류하지 않는다. HMI의 공유 주소도 이름만 다르다고 독립된 PLC 신호로 세지 않는다. 원시 입력과 처리 비트, HMI 요청과 PLC 출력, 오류 해제와 재기동을 분리한다.
6. 현행 모델·정상 극성·설정값·안전 한계·정비 주기·토크는 해당 제조사/명판/승인 자료 없이 채우지 않는다. 외부 기술 조사가 필요하면 제조사 원문을 확인하고 판본·날짜를 기록한다.
7. 충돌은 기존 대장을 보존하고 출처·상충 내용·추가 증거를 기록한다. 기존18불일치/1060확인 대기/577설계 시험을 새 검증 결과 없이 해결·실행 완료로 바꾸지 않는다.
8. 사용자 운영 기록·사진·SEJIN 데이터와 인증정보는 공개 Git으로 복사하지 않는다. 필요한 연결 정보는 허용된 읽기 전용 참조 범위만 사용한다.

| 순서 | 결과물 | 통과 기준 |

| 착수 | 대상 ID·기준 커밋·유형·범위·영향 파일·백업 | 다른 설비/원본/사용자 dirty 보존 |
| 원본 조사 | 7영역 적용표·근거표·조건/회로/알람·누락 목록 | 각 핵심 주장에 원본 위치; 소유/추정 구분 |
| 작성 | 설비별 프로파일·기존 문서·수리/관찰 연결 | 단순 이름 치환 없음; 기존 완료 자료 유지 |
| 독립 검토 | 원본/논리 조사와 결과 대조 | 중요 오류 수정 후 재확인; 검토자·근거 기록 |
| 정적 검증 | 해당 설비 검사 + BC01 회귀 + 필수 검사 | 실패 숨김/단언 완화 없음; 원본/중지 해시 유지 |
| 화면/기록 | 아래 UI·보존 검증 | 실제 저장·재열기 증거; 미검증 항목 분리 |
| 게시/인계 | 버전·변경 이력·GitHub/게시 근거·다음 작업 | 실제 커밋·파일·상태 확인 후 완료 표기 |

기본 분업은 부모가 설계·편집·통합·최종 검증, 최대2개 읽기 전용 조사자가 원본/논리와 독립 검토를 담당한다. 하위 조사도 GPT-6.1 Sol / Ultra를 사용할 수 있을 때 명시한다. 여러 에이전트가 공통 JS/JSON/진행 기록을 동시에 수정하지 않는다. 다른 모델로 자동 대체하지 말고 사용 가능한 설정과 제한을 보고한다.

### 네 기능과 기록 보존

설비별로 도면·래더 나란히 보기, 백업 미리보기/선택 복원, 전후 기록 비교, 관찰 보고서/PDF 적용 여부를 정한다. 근거가 없거나 기능이 구현되지 않은 경우 그 이유와 상태를 표시한다.

기존 note·repair_observation·미지 행/필드·다른 설비·초안·저장 키를 보존한다. 0과 빈칸을 구분한다. generated_with는 생성 시점, saved_with는 저장 시점의 프로그램/근거 정보이며 관찰 당시 CPU나 현장 상태의 증명이 아니다. 과거 기록에 새 근거를 소급 적용하지 않는다.

복원은 미리보기 → 충돌 선택 → 저장 → 재읽기 → 화면 재열기까지 검증한다. 선택 설비 외 기록이 바뀌면 실패다. 동시 탭, 저장 실패, 구형 JSON, 알 수 없는 필드, 중복/잘못된 입력을 시험한다. 현재 Web Locks 없는 환경에서 복원 저장을 막는 정책을 회귀로 보존한다. 실제 사용자 기록 대신 격리한 합성 QA 자료를 사용하고 시험 후 정리한다.

### 화면 검증

PC1280·모바일390에서 기본/큰 글자, 선택 목록/본문/넓게 보기를 확인한다. 모든 적용 항목의 링크 목적지·실제 원본 위치, 왕복·새로고침·선택 복원, 검색/별칭/본문 강조/빈 결과/특수문자/잘못된 URL을 확인한다. 저장·재열기·전후 비교·보고서 변경 감지와 PDF 렌더를 확인한다. 콘솔 문제는 출처와 영향을 기록하고 앱 밖 오류도 근거 없이 0건으로 표시하지 않는다.

공통 UI/기록/라우팅/생성기를 바꿀 때는 BC01 전체 회귀와 영향을 받는 기존 완료 설비를 확인한다. 같은 변경 없는 범위를 이유 없이 반복 검사하지 않는다.

### 검증과 패키지

실행 전 scripts와 생성기 호출을 읽는다. 다음 명령은 용도가 다르다.

    npm run check:python
    npm run verify:bc01
    npm run verify:manual
    npm test
    npm run build

verify:manual은 필수14정적 검사와 manifest·검증 보고서·버전 ZIP을 **재생성**한다. 원본/추가 원본/중지5자산 해시, 파일 목록 양방향 대조, ZIP CRC/전체 SHA를 확인한다. 새 패키지 파일은 검토한 정확한 상대경로 JSON을 GME_NEW_PACKAGE_FILES에 해당 실행에만 지정하고 해제한다. NETLIFY 환경에서도 CSP가 일치해야 한다.

표준/스킬처럼 all-in-one 밖 문서만 바꾸면 매뉴얼 생성기·패키지 재생성을 하지 않는다. 변경에 맞는 문서 링크/스킬 구조/대장 검사만 수행한다.

## 7. 완료 상태와 인계

한 개의 완료 불리언으로 합치지 않는다.

| 상태 | 뜻 | 기본값 |
|---|---|---|
| documentation | 적용영역 작성·근거/누락 명시 | not_started |
| static_review | 원본과 정적 검증 | not_run |
| ui_records | 화면·저장·재열기·PDF | not_run |
| publication | 해당 커밋 실제 게시 | not_published |
| tia_compile | Windows/TIA 컴파일 | not_performed |
| live_cpu | 현재 프로젝트/CPU 비교·동작 | not_performed |
| field_recovery | 실물/관찰/복구 확인 | not_performed |

문서가 complete_with_gaps여도 TIA/CPU/현장 확인은 별도 상태로 남긴다. 적용되는 기능이 미구현이면 BC01 동등 표준화 완료라고 쓰지 않는다. 설계된 시험과 실행된 시험을 구분한다. 새 현장 자료 없이 field_verified나 repairs_completed를 true로 만들지 않는다.

작업마다 기준 커밋, 실제 실행 모델/추론 수준(관측 불가면 미확인), 대상, 수정 파일, 수행 검사, 남은 문제, 다음 한 작업을 기록한다. EXPANSION-WORK.md를 먼저 갱신하고 기능을 게시했으면 all-in-one/ACTIVE-WORK.md·VERSION·RELEASES·PUBLICATION_STATUS도 실제 결과에 맞춘다.

프로그램 VERSION(root/all-in-one)/package/lock/생성기/manifest는 기능 릴리스 때 일치시킨다. 이 작업표준은 별도 GME-STD 버전으로 관리하며 현재 프로그램 v1.3.0을 문서만으로 올리지 않는다. main은 최신 작업, 고정 태그는 불변 기준이다. 버전마다 근거·검증·미확정 범위를 남기고 기존 태그를 덮어쓰지 않는다.

다른 컴퓨터는 [START-GPT61.md](START-GPT61.md)의 clone/pull → 표준 읽기 → preflight → 최신 작업 기록 확인 순서로 재개한다. GitHub 소스 동기화와 브라우저 관찰 기록 이동은 별도다. 브라우저 기록은 Git에 올라가지 않으며 현재 v1.3.0의 타 설비 복원은 아직 구현되지 않았다.
